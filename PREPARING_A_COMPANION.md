# Preparing a companion

Start with a real body of work and the people who might encounter it. The preparation should make useful conversation possible from the file itself, then make deeper inspection easy when it matters.

## 1. Know what you are introducing

Read the material, speak with the people responsible, and establish the companion's scope. A guide to one project and an introduction to an institution need different amounts of context.

Identify the actual works, offers, people, sources, and open questions. Keep the difference between a present capability and an intended extension understandable.

## 2. Compose an account someone can recognize

Explain the subject in ordinary language. Give concrete examples before relying on categories such as innovation or expertise. When the file represents an institution or person, let them review whether the account is recognizable and accurate.

Include the relationships that make the parts useful together. A publication may demonstrate a method; a garden may lead to production code and teaching; a public explanation may lead to a source collection. Those connections are part of what the author contributes.

## 3. Give the receiving assistant a useful appointment

Explain that the person has supplied the preparation for exploring the subject. The assistant works with that person's interests.

Help it answer the actual question, use its prepared knowledge proportionately, welcome disagreement, and offer a relevant next source when useful. Let a satisfying answer or enjoyable visit be enough.

Place this guidance near the beginning so the receiving assistant understands the file's job before using its detailed account.

## 4. Make routes practical

Give exact names and usable destinations. State what each deeper resource would help answer and whether it is public, available on request, or only proposed.

Use a small source register rather than forcing every answer to recite production records. A meaningful distinction should be available when it changes what the reader should believe, obtain, or do.

## 5. Separate the shared account from personal context

Keep reusable knowledge about the subject identifiable. Put recipient-specific context in a separate section or note: who supplied it, when, and what the recipient actually expressed.

A sender's reason for making an introduction is useful context. It does not establish what the recipient wants. Leave room for their first question to change the starting emphasis.

## 6. Read it as a recipient

Check whether someone can begin from the file alone, locate the named objects, and follow the instructions without knowing your internal vocabulary.

When trying the file in another conversation, notice what it helps the person understand and where the return is confusing, repetitive, overconfident, or unnecessarily demanding. Use that experience to revise the preparation. Record any reported trial at its actual scope; a useful conversation is not automatically evidence of universal performance.

The [starter](template/README.md) supplies a structure for a first draft. The [accepted Meet MFL example](examples/meet-mfl-0.4/README.md) shows a substantially developed account.

## 7. Maintain it as an authored work

Give the file a stable name, edition, source date, and responsible maintainer. Review it when the underlying works, access, offers, relationships, or instructions change in ways that affect a recipient.

Keep the companion edition distinct from a repository release. One method release can include an example companion with its own established edition.

The file should remain easy to obtain and inspect. A readable repository page, raw text download, and a fixed example ZIP serve different practical uses.
